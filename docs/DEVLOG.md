## [2026-04-10] Этап 0: Фундамент и Видение

### 🎯 Цель этапа
Сформулировать концепцию MVP и определить "Скучную Архитектуру" (Boring Architecture), которая выдержит рост до 1 млн пользователей.

### ✅ Что сделано
- Изучен контекст: Сервис для мамы, который должен превратиться в масштабируемый продукт.
- Выбран стек: **Next.js (App Router)** + **TypeScript** + **PostgreSQL** + **Drizzle ORM**.
- Определена инфраструктура: **Yandex Cloud** (Compute, S3, Vision OCR, YandexGPT).
- Спроектирована схема БД: Акцент на `service_records` и `work_items` с поддержкой JSONB для сырых данных OCR.

### 🏗 Архитектурные решения
1. **Выбор Drizzle ORM вместо Prisma**: Для максимального контроля над SQL и производительности, что критично при планах на 1 млн юзеров.
2. **Гибридный OCR**: Использование Yandex Vision для текста + YandexGPT для превращения "каши" из слов в структурированный JSON. Это дешевле и гибче, чем готовые сервисы парсинга чеков.
3. **Хранение в S3**: Оригиналы накладных — это юридическая и историческая ценность, поэтому сразу заложили S3 с политикой жизненного цикла (Cold Storage).

### 💡 Инсайты
- Проект вдохновлен реальной болью (папка с накладными за 10 лет). Это дает четкий критерий успеха: "Сможет ли мама этим пользоваться?".
- Главный риск — качество распознавания старых или мятых накладных. Поэтому в схему БД заложен статус `manual` для ручной корректировки.

### 🏁 Что дальше?
Переход к реализации базового каркаса приложения и настройки окружения.

## [2026-04-17] Этап 4: Milestone 1 — Оживление "Ядра" (OCR Core Loop)

### 🎯 Цель этапа
Реализовать полный цикл оцифровки бумажной накладной: от фото до структурированной записи в БД.

### ✅ Что сделано
- **Личный кабинет (Гараж)**:
  - Создана группа роутов `(dashboard)` с защищенным макетом и серверной проверкой сессии.
  - Реализована страница Гаража с динамическим списком автомобилей.
  - Создана форма добавления автомобиля через модальное окно с использованием `framer-motion` для плавности.
- **OCR Engine (Phase 1)**:
  - Реализован API-маршрут `/api/ocr/analyze` с мок-логикой, имитирующей работу Yandex Vision и YandexGPT (задержка 2.5с + структурированный JSON).
  - Настроен API для загрузки файлов в Yandex S3 через presigned-ссылки.
- **OCR UI (Flow)**:
  - Создан многостадийный компонент `OCRModal` (Idle -> Uploading -> Analyzing -> Review -> Saving -> Success).
  - Реализован интерфейс **Review**, где пользователь может редактировать распознанные данные, список работ и запчастей перед сохранением.
- **База данных**:
  - Реализован эндпоинт для сохранения комплексной записи (Service Record + Work Items).
  - Добавлена логика автоматического обновления текущего пробега автомобиля при добавлении новой записи.

### 🏗 Архитектурные решения
1. **Direct-to-S3 Upload**: Файлы загружаются напрямую с клиента в S3, не нагружая сервер Next.js.
2. **Transaction-like Save**: При сохранении записи данные распределяются по таблицам `service_records` и `work_items`, обеспечивая целостность истории.
3. **Mock-first OCR**: Использование мока на этапе M1 позволило полностью отладить UI/UX и схему данных, не дожидаясь настройки ключей Yandex Cloud.

### 💡 Инсайты
- Процесс "ожидания нейросети" (Analyzing) с хорошим спиннером и описанием того, что происходит, значительно повышает доверие пользователя к результату.
- Автоматическое обновление пробега авто из накладной — маленькая, но очень важная деталь для "магического" UX.

### 🏁 Что дальше?
Переход к Milestone 2: Улучшение визуализации истории (Timeline), просмотр оригиналов чеков и детальная статистика расходов.

- В Tailwind 4 механизм `@theme` полностью переписывает дефолтные цвета, если они не импортированы явно. Это вызвало исчезновение текста, но привело к правильному архитектурному решению: использовать только CSS-переменные проекта.
- Динамика (пульсирующие точки в шагах, анимированный сервер в безопасности) и правильные отступы играют ключевую роль в восприятии продукта. 120px между блоками — оптимальный стандарт для современного веба.

## [2026-04-30] Этап 6: Инфраструктурный прорыв и Backend Core

### 🎯 Цель этапа
Оживить "мозг" системы: настроить реальную связь с Yandex Cloud (OCR + GPT + S3) и развернуть постоянную базу данных в Supabase.

### ✅ Что сделано
- **Инфраструктура Yandex Cloud**:
  - Настроены и проверены **API-ключи** для нейросетей и **Статические ключи** для S3.
  - Решена проблема `code 16 (Unknown API Key)` путем активации биллинга и корректного распределения ролей (`ai.vision.user`, `storage.editor`).
  - Успешно протестирована загрузка файлов в Yandex Object Storage (S3).
- **OCR & AI Pipeline**:
  - Реализован и протестирован полный цикл распознавания: **Yandex Vision** (извлечение текста) -> **YandexGPT** (структурирование в JSON).
  - Подтверждено высокое качество распознавания на реальных чеках за период 2014-2025 гг. (включая рукописные пометки и сложные таблицы).
- **База данных (Supabase)**:
  - Описана финальная схема Drizzle: `users`, `vehicles`, `service_records`, `work_items`.
  - Реализована поддержка статусов записей (`draft`, `processed`, `manual`).
  - База успешно развернута в **Supabase**, применены миграции.
  - Проведен успешный тест сохранения: данные из OCR-пайплайна теперь автоматически попадают в таблицы БД.

### 🏗 Архитектурные решения
1. **Separation of Keys**: Использование разных типов ключей (API vs Static) для безопасности и соответствия стандартам Yandex Cloud.
2. **AI-Driven Data Entry**: Вся тяжелая логика парсинга переложена на YandexGPT, что позволяет использовать дешевый тариф Vision OCR (`TEXT_DETECTION`) вместо дорогого табличного.
3. **Master Pipeline Script**: Создан унифицированный скрипт-оркестратор, который объединяет загрузку, распознавание и сохранение в одну атомарную операцию.

### 💡 Инсайты
- Yandex Vision + YandexGPT — это "киллер-фича". Качество разбора чека 10-летней давности с точностью до копейки и артикула запчасти подтверждает жизнеспособность продукта.
- Конфигурация прав в Облаке — это самый сложный этап. "Прозрачность" тарификации и мониторинга в Яндексе помогает контролировать расходы на MVP.

### 🏁 Что дальше?
С бэкенд-ядром покончено. Следующий шаг — интеграция этого ядра во Frontend: создание страницы загрузки чека и ленты истории в Личном кабинете.
